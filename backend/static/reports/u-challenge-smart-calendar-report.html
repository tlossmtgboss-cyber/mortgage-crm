Critical Findings (7 issues — fix immediately)

C1: Email Suppression List Stored In-Memory — Wiped Every Deploy CRITICAL

The email bounce/complaint suppression list is a Python dict protected by a threading.Lock. Every Railway deployment restarts the process, wiping all suppressions. Previously bounced emails get re-sent, damaging sender reputation and risking ESP account suspension.

backend/routes/scheduler/email_events.py:48-49

Impact: SendGrid domain reputation degradation. Bounce rate spikes after deploys. Potential ESP account suspension.

Move to database table (EmailSuppression model) or Redis SET with no TTL. The comment on line 40-43 literally says "production would use a DB table" — this was never done.
C2: Forgeable Unsubscribe Tokens — Plain Base64, No HMAC CRITICAL

Unsubscribe tokens are base64.urlsafe_b64encode(email) with no signature. Any attacker can construct a valid unsubscribe token for any email address, suppressing legitimate recipients without their knowledge.

backend/routes/scheduler/email_events.py:148-153

Attack: base64.urlsafe_b64encode("ceo@client.com".encode()) → POST to /email-events/unsubscribe/{token} → CEO stops receiving all appointment emails.

Sign tokens with HMAC-SHA256 using SECRET_KEY. Token format: base64(email) + "." + hmac_hex. Verify signature before processing.
C3: No SendGrid Webhook Signature Verification CRITICAL

The SendGrid webhook endpoint (/email-events/sendgrid) reads SENDGRID_WEBHOOK_VERIFICATION_KEY from env but never uses it. Any HTTP client can POST fake bounce events to suppress arbitrary email addresses.

backend/routes/scheduler/email_events.py:36,86-127

Attack: POST a JSON array with [{"event":"bounce","email":"target@company.com"}] to the public endpoint. No auth required.

Implement SendGrid's Event Webhook signature verification: verify the X-Twilio-Email-Event-Webhook-Signature header using the verification key with ECDSA. Reject requests that fail verification.
C4: Email Rate-Limit Bypass — org_id Never Passed CRITICAL

Public booking endpoints call _send_booking_confirmation_email() without passing org_id, so the email rate limiter uses a global bucket instead of per-org. A single org's burst can exhaust the global rate limit, blocking emails for all tenants.

backend/routes/scheduler/public_booking.py — all email-sending call sites

Impact: Multi-tenant email denial-of-service. One org's booking spike blocks confirmation emails for all other orgs.

Pass org_id to all email service calls from public_booking.py. Rate limit key should be f"email_rate:{org_id}" not global.
C5: Webhook Auto-Retry Uses Wrong Attribute — Silently Broken CRITICAL

The webhook retry logic in scheduler_service.py references webhook.endpoint_url but the SchedulerWebhookConfig model defines the column as url. Every retry raises AttributeError, caught by a bare except, and silently fails. Webhook retries have never worked.

backend/services/scheduler_service.py — webhook retry method

Impact: Failed webhooks are never retried. Dead-letter queue grows silently. Integration partners miss appointment events.

Change webhook.endpoint_url to webhook.url throughout the retry method. Add a test that actually triggers a retry.
C6: asyncio.gather Shares Single DB Session Across Coroutines CRITICAL

scheduler_webhook_service.py uses asyncio.gather() to fire multiple webhook deliveries concurrently, but all coroutines share the same SQLAlchemy Session object. SQLAlchemy sessions are not thread-safe or coroutine-safe — concurrent commits/rollbacks corrupt transaction state.

backend/services/scheduler_webhook_service.py

Impact: Random InvalidRequestError, partial commits, and data corruption under concurrent webhook delivery.

Each coroutine in asyncio.gather must get its own session via get_db(). Or use a session-per-request pattern with async session factory.
C7: Reschedule Token Reusable for 72 Hours, No Ownership Check CRITICAL

Borrower reschedule tokens are valid for 72 hours and can be used unlimited times. There's no check that the token was issued for the person using it. Tokens contain appointment_id but no borrower identifier — anyone with the link can reschedule anyone's appointment.

backend/routes/scheduler/reschedule.py

Impact: Appointment manipulation. Forward a reschedule link → recipient can move someone else's appointment.

1. Single-use: mark token as used after first reschedule. 2. Bind to borrower: include borrower_email in token payload and verify on use. 3. Reduce TTL to 24 hours.

High Findings (17 issues — address this sprint)

H1: X-Forwarded-For Rightmost IP Is Proxy, Not Client HIGH

Rate limiting extracts client IP from X-Forwarded-For using the rightmost entry, which is the last proxy (e.g., Cloudflare or Railway's load balancer). Real client IP is leftmost. All rate limiting is per-proxy, not per-client.

backend/routes/scheduler/_rate_limiting.py

Use leftmost X-Forwarded-For entry, or better: use CF-Connecting-IP header which Railway/Cloudflare sets to the true client IP.
H2: Advisory Lock Failure Silently Continues Booking HIGH

When pg_try_advisory_xact_lock() fails after 3 retries (0.9s), booking proceeds with only a logger.warning(). Two concurrent bookings for the same slot can both succeed.

backend/routes/scheduler/_conflicts.py

Raise HTTPException(409, "Slot temporarily locked, please retry") when lock acquisition fails after retries.
H3: Cross-Source Availability Fails Open HIGH

The 4-source calendar reconciliation (scheduler + legacy + manual + Salesforce) catches all exceptions during cross-source conflict checking and returns an empty conflict set. If any source query fails, those conflicts are invisible — the slot appears available.

backend/routes/scheduler/_availability.py

On cross-source failure: either fail closed (mark slot unavailable) or return a "degraded" flag so the UI can warn the user.
H4: Bulk Operations Race Condition — Intra-Batch Blindness HIGH

Bulk create/reschedule processes items sequentially within a batch, but conflict detection for item N doesn't see items 1 through N-1 that were created earlier in the same batch (not yet committed). Double-booking within a single bulk request is possible.

backend/routes/scheduler/bulk_operations.py

db.flush() after each item creation to make it visible to subsequent conflict checks within the same transaction. Or collect all times first and validate the batch internally before any writes.
H5: Demo Booking Leaks Tenant Configuration HIGH

The demo booking flow at /public/book-demo/confirm returns the full org's scheduler configuration (working hours, appointment types, notification settings) to unauthenticated users when rendering the demo form.

backend/routes/scheduler/public_booking.py

Return only the minimum fields needed for the demo booking form: available time slots and appointment type names. Strip all internal configuration.
H6: Cancel Endpoint Missing Status Validation HIGH

The cancel endpoint allows cancelling appointments that are already in terminal states (COMPLETED, NO_SHOW, CANCELLED). Cancelling a COMPLETED appointment re-triggers notification chains and corrupts audit trail.

backend/routes/scheduler/appointments.py

Check current status before allowing cancel. Only BOOKED, CONFIRMED, and REMINDED should be cancellable.
H7: Audit Log Write Failures Silently Swallowed HIGH

Multiple audit logging call sites wrap _audit_log() in bare try/except blocks. If the audit table is full, has schema drift, or the transaction is in a bad state, the audit write fails silently and the operation proceeds without any audit record.

backend/routes/scheduler/_audit.py, backend/routes/scheduler/_helpers.py

At minimum: logger.error() with exc_info=True on audit failures. For compliance-critical operations (cancel, reschedule, data deletion), audit failure should abort the operation.
H8: No-Show Recovery db.rollback() Wipes Prior Flushes HIGH

The no-show recovery service calls db.rollback() in error handlers after prior db.flush() calls within the same transaction. This wipes not just the failed operation but all pending changes from earlier recovery steps in the same batch.

backend/services/no_show_recovery.py

Use SAVEPOINT (db.begin_nested()) before each recovery step. On failure, rollback to savepoint, not the entire transaction.
H9: Webhook HMAC Verification Uses Wrong Comparison HIGH

Webhook signature verification computes HMAC-SHA256 but the comparison of received vs expected signature doesn't consistently use hmac.compare_digest(). Some code paths use ==, which is vulnerable to timing attacks.

backend/services/scheduler_webhook_service.py

Replace all == comparisons on HMAC values with hmac.compare_digest() for constant-time comparison.
H10: No SSRF Protection on Webhook URL Registration HIGH

Users can register any URL as a webhook endpoint, including internal network addresses (http://169.254.169.254/, http://localhost:5432/). The webhook delivery service will POST to these URLs from the server's network context.

backend/services/scheduler_webhook_service.py, backend/routes/scheduler/webhooks.py

Validate webhook URLs against a blocklist: no RFC 1918/RFC 4193 addresses, no localhost, no link-local, no metadata endpoints. Require HTTPS.
H11: No-Show Recovery Tracking via Regex on Free-Text HIGH

The no-show recovery system tracks which recovery step was last executed by parsing free-text notes fields with regex. If the note format changes or contains unexpected characters, step tracking breaks and recovery restarts from step 1.

backend/services/no_show_recovery.py

Add a recovery_step integer column to the appointment or a dedicated recovery_tracking table. Never rely on regex parsing of human-readable text for state management.
H12: Compliance Service N+1 Queries HIGH

compliance_scheduling_service.py loads appointments in a list query, then makes individual queries for each appointment's borrower consent status, LO notification preferences, and DNC checks. For a batch of 50 appointments, this generates 150+ queries.

backend/services/compliance_scheduling_service.py

Batch-load consent status, LO prefs, and DNC status in 3 queries using WHERE id IN (:ids), then join in Python.
H13: No DST Handling in Recurring Availability HIGH

recurring_availability_service.py computes availability using naive datetime arithmetic without DST transition handling. On spring-forward/fall-back days, slot times shift by 1 hour or generate invalid/duplicate slots.

backend/services/recurring_availability_service.py

Convert all time arithmetic to timezone-aware datetimes using pytz or zoneinfo. Compute slots in the LO's local timezone, then convert to UTC for storage.
H14: nh3 Fallback to html.escape Is Not Equivalent HIGH

Input validation falls back from nh3.clean() to html.escape() on ImportError. nh3 strips dangerous HTML entirely; html.escape converts <script> to &lt;script&gt; which is then rendered as visible text in emails, not sanitized.

backend/routes/scheduler/_input_validation.py

If nh3 is not available, raise an ImportError at startup rather than silently falling back to a weaker sanitizer. nh3 is a hard dependency for security.
H15: Email Templates Vulnerable to XSS HIGH

notification_service.py constructs HTML emails using f-strings with user-provided data (borrower name, appointment notes) without HTML escaping. A borrower name like <img src=x onerror=fetch('...')> executes in the recipient's email client.

backend/services/notification_service.py

HTML-escape all user-provided values before inserting into email templates. Use html.escape() or a proper template engine with auto-escaping (Jinja2).
H16: Google Token Refresh Doesn't Update expires_at HIGH

When the Google Calendar OAuth token is refreshed in virtual_meeting_service.py, the new access token is saved but expires_at is not updated. The next check sees the old (expired) timestamp and triggers another refresh — creating a refresh loop on every request.

backend/services/virtual_meeting_service.py

After token refresh, update both access_token AND expires_at = datetime.now(timezone.utc) + timedelta(seconds=expires_in).
H17: AvailabilitySlot Unique Constraint Allows Duplicate Date Overrides HIGH

The AvailabilitySlot model's unique constraint doesn't cover date-specific overrides adequately. Two overrides for the same date, same org, same user can coexist — queries pick one arbitrarily.

backend/database/models/scheduler.py

Add UniqueConstraint('organization_id', 'user_id', 'override_date') or enforce via application-level upsert.
