The Smart Calendar is an ambitious, feature-rich scheduling system with 171 routes across 32 modules — far more comprehensive than most embedded scheduling solutions. Its architecture (decomposed routers, service layers, defense-in-depth booking protection) is sound at the macro level. However, the rapid feature expansion has outpaced security hardening, testing, and operational resilience. 8 critical findings require immediate attention before this system can be trusted with production mortgage scheduling at enterprise scale. The dual availability source ambiguity and Turnstile replay vulnerability are the most dangerous — they can silently cause double-bookings and bot abuse respectively.

Critical Findings (8)

C1
Turnstile CAPTCHA Replay Bypass in Multi-Worker Deployments
_input_validation.py — The Turnstile anti-replay cache is a per-process Python set() with no TTL or cross-worker coordination. In any deployment with >1 worker (Gunicorn, Uvicorn workers, horizontal scaling), a valid Turnstile token can be replayed to a different worker. This completely defeats bot protection on public booking endpoints, allowing automated slot squatting and waitlist spam.

Impact: Bots can book all available slots, preventing real borrowers from scheduling. Public waitlist can be flooded with fake entries.
Fix: Replace in-memory set with Redis SETNX (TTL=300s). If Redis unavailable, use DB-backed nonce table with periodic cleanup. Minimum viable: add a TTL eviction to the in-memory cache and document the single-worker limitation.
C2
Advisory Lock Error Silently Swallowed
_conflicts.py — The PostgreSQL advisory lock acquisition (pg_try_advisory_xact_lock) catches all exceptions with a bare except Exception and silently continues without the lock. If the lock fails (connection issue, parameter error), the double-booking prevention layer is completely bypassed — the code proceeds as if the lock was acquired. The SELECT FOR UPDATE + unique index provide backup, but advisory locks exist precisely because those layers have edge cases.

Impact: Under contention (two users booking the same slot simultaneously), the advisory lock layer — the first line of defense — silently fails, increasing double-booking risk.
Fix: Log the exception at WARNING level. If the lock cannot be acquired (not just fails to try), raise a 409 Conflict immediately rather than proceeding unprotected.
C3
Calendar Feed Token Never Expires
calendar_feed.py — The iCal feed subscription token is generated without an exp claim in the JWT payload. Once issued, it is valid forever. Unlike other scheduler tokens (confirmation=48h, cancel=72h, waitlist=7d), the calendar feed token has no expiry. If a user leaves the organization or their account is deactivated, the feed token remains valid and continues exposing their calendar data.

Impact: Former employees retain perpetual read access to organization calendar data. No mechanism to revoke access short of rotating the global SECRET_KEY.
Fix: Add exp claim (30-90 day rolling window). Implement token refresh on feed access. Add per-user token revocation (store issued_at in DB, reject tokens issued before revocation timestamp).
C4
Dual Availability Source Ambiguity
_availability.py:344-366 — Two completely independent availability sources coexist: SchedulerConfig.working_hours (JSON blob) and the RecurringAvailability table. If RecurringAvailability rows exist, the JSON blob is silently ignored. But the settings UI writes to the JSON blob, and the availability management UI writes to RecurringAvailability. A user who sets availability in Settings, then later adds a single exception via the Availability UI, will unknowingly switch their entire availability source — potentially showing completely different hours than they configured.

Impact: LOs can unknowingly have wrong availability published on their booking pages, leading to missed appointments or overbooking.
Fix: Merge both sources with explicit precedence rules and display a warning in the UI when both sources have data. Long-term: deprecate the JSON blob in favor of RecurringAvailability only.
C5
No Rate Limiting on Calendar Sync Webhook Endpoints
calendar_sync_inbound.py — The Google Calendar push notification receiver (/calendar/sync/google/webhook) and Outlook Graph change notification receiver (/calendar/sync/outlook/webhook) have no rate limiting. While they validate signatures, a misconfigured or malicious webhook source could send thousands of notifications per second, each triggering database queries and potentially full calendar re-syncs.

Impact: Database connection exhaustion. Railway's 20-connection pool limit means ~20 concurrent sync webhooks could saturate the pool and bring down the entire application.
Fix: Add rate limiting (100 req/min per provider per org). Queue incoming webhooks for batch processing. Add circuit breaker that stops processing if error rate exceeds threshold.
C6
Compliance Scheduling Service Hardcoded Timezone
compliance_scheduling_service.py — The TCPA contact-hours enforcement uses a hardcoded timezone assumption rather than the borrower's actual timezone. For a mortgage CRM that operates across all US time zones, this means TCPA contact-hour violations are possible for any borrower not in the hardcoded timezone. TCPA violations carry $500-$1,500 per call in statutory damages.

Impact: Potential TCPA violations with statutory damages of $500-$1,500 per non-compliant contact. Class action exposure for systematic timezone errors.
Fix: Resolve borrower timezone from their property state or explicit timezone field. Fall back to the most restrictive interpretation (latest start, earliest end) when timezone is unknown.
C7
Frontend Timezone Handling Inconsistencies
Calendar.js, BorrowerAppointmentView.js, EmbeddableBookingWidget.js — Multiple frontend components handle timezone conversion independently with inconsistent approaches. Some use Intl.DateTimeFormat, some use manual UTC offset math, and some don't handle timezones at all. The booking widget displays times in the browser's local timezone but sends UTC to the API without clearly indicating the conversion — borrowers in different timezones than their LO can book appointments at unintended times.

Impact: Borrowers book appointments at wrong times. LOs see appointment times that don't match what the borrower expected.
Fix: Centralize timezone handling in a shared utility. Always display times with explicit timezone labels. Store and transmit timezone alongside all datetime values.
C8
Missing Composite Indexes on High-Frequency Queries
scheduler.py — While the Appointment model has 11 indexes (including the conflict-check and double-booking indexes), several high-frequency query patterns lack composite indexes: (1) WaitlistEntry queries by (organization_id, status, appointment_type_id) do sequential scans; (2) SchedulerAuditLog queries by (organization_id, entity_type, created_at) lack a covering index; (3) CalendarEventMap lookups by (provider, external_id, organization_id) rely on individual column indexes rather than a composite.

Impact: Query latency degrades as data grows. At enterprise scale (10K+ appointments, 50K+ audit logs), these sequential scans will cause visible slowdowns and connection pool contention.
Fix: Add 3 composite indexes: ix_waitlist_org_status_type, ix_audit_org_entity_created, ix_calendar_map_provider_ext_org.

High Findings (12)

H1
Missing is_active Check in Auth Helper
_auth.py — get_current_user validates the JWT and loads the user but does not check user.is_active. Deactivated users retain full scheduler access until their JWT expires.
H2
Three Independent Appointment Creation Paths
appointment_creation_service.py, appointment/service.py, pipeline_appointment_trigger.py — Each has its own validation, conflict checking, and notification logic. Bug fixes applied to one path may not reach the others. The creation service lacks explicit transaction atomicity (no db.begin() or savepoint).
H3
Webhook Service Session Management
scheduler_webhook_service.py — Creates its own DB sessions instead of using the request-scoped session from FastAPI's Depends(get_db). If the webhook fires within a request handler, there are now two independent sessions — the webhook's session can commit data the request session doesn't see, or vice versa.
H4
Email Events Route Missing Org Scoping
email_events.py — The email event tracking endpoint writes records with organization_id=NULL when the event comes from a public booking confirmation email. These orphaned records are invisible to org-scoped queries, creating a data integrity gap in email delivery tracking.
H5
NMLS Validation Bypass in CRM Integration
_crm_integration.py — When creating a CRM lead from a public booking, the NMLS license verification for the assigned LO is skipped if the lookup fails. This means an unlicensed LO can receive leads through the scheduler without any warning.
H6
Confirmation Router Missing Cancel/Reschedule from Token
confirmation.py — The confirmation token grants access to view appointment details but there are no POST /public/confirm/{token}/cancel or /reschedule endpoints. Borrowers who receive a confirmation email cannot cancel or reschedule from that link — they must use a separate reschedule link (if one was sent) or contact their LO directly.
H7
N+1 Query in Recurring Availability Check
_availability.py:462-475 — For each date in the requested range, a separate query checks for date-specific exceptions in RecurringAvailability. A 30-day availability request generates 30 individual queries. At scale this causes noticeable latency on the public booking page.
H8
No Circuit Breaker on External Calendar API Calls
_availability.py:69-176 — External calendar conflict checks (Google, Outlook) have a fail-closed pattern (timeout = entire range conflicted), but no circuit breaker. If Google Calendar API is down, every slot query for every user hits the timeout, degrading the entire system. After N consecutive failures, should skip external checks temporarily.
H9
Slot Hold Expiration Relies on Periodic Cleanup
maintenance.py — Expired SlotHold records are cleaned up by a manual admin endpoint (/maintenance/cleanup-holds), not by automatic background processing. If nobody hits this endpoint, expired holds accumulate and phantom-block slots from being booked.
H10
Inconsistent Error Response Formats Across Public Endpoints
Public endpoints use a mix of raise HTTPException directly and the standardized error_responses.py helpers. Some return {"detail": "..."}, others return {"error": "...", "code": "..."}. Frontend must handle both formats, and the inconsistency makes it harder to display meaningful error messages to borrowers.
H11
Survey Response Endpoint Lacks Duplicate Submission Guard
surveys.py — The public survey response endpoint accepts multiple submissions from the same token/email combination. A borrower (or bot) can submit dozens of survey responses, skewing satisfaction metrics.
H12
Frontend State Management — No Optimistic Updates
Calendar.js — All booking actions wait for the API round-trip before updating the UI. On slow connections, users see no feedback for 1-3 seconds after clicking "Book", leading to double-clicks and duplicate booking attempts. The frontend should optimistically update the calendar view and roll back on failure.

Medium Findings (18)

M1
No Structured Logging in Scheduler Subsystem
All 32 modules use Python's basic logger.info/warning/error with unstructured string messages. No correlation IDs, no structured JSON fields. Debugging a failed booking across availability check → conflict detection → appointment creation → notification → webhook requires grep-fu across unstructured logs.
M2
Test Coverage at ~15% Endpoint Coverage
45 test files with 750+ test cases exist, but they cover only ~15% of the 171 scheduler endpoints. Zero integration tests for the critical public booking flow. No load/stress tests. The test files are well-structured but the gap means regressions can ship undetected.
M3
Appointment Type Configuration Sprawl
AppointmentType model has 40+ columns covering duration, buffer, location, notifications, branding, CRM integration, and feature flags. This is a "god object" that would benefit from decomposition into separate concerns (scheduling rules, branding, integration config).
M4
Public Booking Page Bundle Size
The embeddable booking widget imports the full React app context including calendar components, analytics dashboards, and admin utilities via shared imports. The public booking page, which should be lightweight for SEO and borrower experience, likely ships 500KB+ of unused JavaScript.
M5
No Health Check for External Calendar Sync Status
The /health endpoint checks DB connectivity but not Google/Outlook Calendar API reachability. An admin has no way to know if calendar sync is silently failing without checking individual user sync timestamps.
M6
Cancellation Policy Enforcement Gap
cancellation_policy.py enforces policies on the dedicated cancel endpoint, but direct status changes via the appointment CRUD endpoint (PATCH /appointments/{id}) can bypass cancellation policy checks by setting status="cancelled" directly.
M7
SEO Sitemap Generates All Booking Links Without Pagination
sitemap.py queries all active booking links and generates a single XML sitemap. At enterprise scale (1000+ booking links), this generates an oversized sitemap that search engines may truncate or reject.
M8
Reminder Service Lacks Idempotency
reminder_service.py — If the reminder cron job runs twice (restart, overlap), duplicate reminders are sent. No sent-status tracking prevents re-sending the same reminder.
M9
No Appointment Capacity Limits Per Type
There's no per-day or per-week capacity limit on appointment types. An LO with 8 hours of availability could theoretically have 16 back-to-back 30-minute appointments booked, with no breathing room beyond configured buffer times.
M10
Widget Configuration Not Cached
widget_config.py — Every public booking widget page load queries the full appointment type configuration, org branding, and available slots. No caching layer means repeated page views by the same borrower (or a Google bot) all hit the database.
M11
Audit Log Table Will Grow Unbounded
SchedulerAuditLog has no partition strategy or retention policy. Every booking, cancellation, reschedule, and settings change generates an audit record. At enterprise scale, this table will grow to millions of rows with degrading query performance and no automated archival.
M12
No Appointment Deduplication Window
The unique index prevents exact-duplicate bookings (same user, same time, same type), but there's no "cooling off" period. A borrower can book a consultation for 10am, cancel it, and immediately rebook for 10:15am, then cancel again — cycling through all available slots.
M13
Frontend Calendar Component Monolith
Calendar.js is a single component handling day/week/month views, appointment CRUD, drag-and-drop, notifications, and analytics integration. At ~800+ lines, it's becoming difficult to maintain and test individual concerns.
M14
No Webhook Delivery Dashboard
WebhookHealthDashboard.js exists but only shows basic delivery stats. No per-endpoint success/failure rates, no payload inspection, no manual retry from the UI. Debugging webhook failures requires direct database queries.
M15
Booking Link Analytics Lack Attribution
booking_links.py tracks views and bookings per link, but doesn't capture UTM parameters, referrer, or source attribution. Marketing teams can't measure which channels drive the most bookings.
M16
No Batch Booking API
The bulk operations module handles batch status changes but not batch booking creation. Enterprise onboarding (importing 50 pre-scheduled appointments from a legacy system) requires 50 individual API calls.
M17
CSS Architecture Fragmentation
Calendar styles are split across Calendar.css, BorrowerAppointmentView.css, calendar-settings.css, and inline styles in multiple components. No CSS modules or CSS-in-JS consistency. Style conflicts are inevitable as components evolve independently.
M18
Incomplete Accessibility on Public Booking Pages
The embeddable booking widget lacks ARIA labels on time slot buttons, keyboard navigation for date/time selection, and screen reader announcements for booking confirmation. Public-facing mortgage scheduling must meet WCAG 2.1 AA for ADA compliance.

What You're Doing Right (7)

S1 — Defense-in-Depth Double-Booking Prevention
Three independent layers: advisory locks, SELECT FOR UPDATE NOWAIT, and a partial unique index. This is textbook correct and better than what most scheduling systems implement. The unique index alone would prevent double-bookings at the database level even if all application logic failed.
S2 — Comprehensive Feature Surface
171 routes across 32 modules covering waitlists, surveys, labels, reschedule flows, cancellation policies, booking link analytics, calendar feeds, calendar sync, SEO sitemaps, and compliance. This is a genuinely full-featured scheduling platform, not a bolt-on calendar widget.
S3 — Clean Router Decomposition
32 focused router modules with a central __init__.py assembly point, shared helpers factored into _auth.py, _availability.py, _conflicts.py, _rate_limiting.py, and _input_validation.py. This is maintainable architecture that scales to a large team.
S4 — Cross-Source Conflict Fail-Closed
When external calendar sources (Google, Outlook) time out, the affected time range is marked as conflicted rather than available. This is the correct default — it's better to show fewer available slots than to double-book against an external calendar.
S5 — Batch-Loaded Slot Generation
The availability engine runs 5 batch queries upfront (appointments, blocked times, slot holds, recurring exceptions, external events) rather than querying per-slot. This avoids the N+1 pattern that plagues most availability calculators.
S6 — Token-Protected Public Endpoints
Public endpoints (waitlist, reschedule, confirmation, surveys) use purpose-scoped JWT tokens rather than exposing sequential IDs. This prevents IDOR attacks on unauthenticated flows — a common vulnerability in booking systems.
S7 — Standardized Error Response Helpers
error_responses.py provides consistent error formatting across the subsystem. While adoption isn't 100% yet (see H10), the infrastructure is there and most authenticated endpoints use it correctly.

Bottom Line

The Smart Calendar is an impressively ambitious system that does more than most embedded scheduling solutions. The architecture is sound, the feature surface is comprehensive, and the defense-in-depth booking protection is genuinely well-designed. But the rapid expansion has created security gaps (Turnstile bypass, eternal tokens, unprotected webhooks), data integrity risks (dual availability sources, phantom slot holds), and compliance exposure (hardcoded timezones for TCPA). Phase 1 fixes are estimated at ~15 hours of engineering work — a modest investment to close the critical gaps.
