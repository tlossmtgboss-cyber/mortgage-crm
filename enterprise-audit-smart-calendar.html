Critical Blockers (8) — Must Fix Before Enterprise Deployment

▶ Critical FUNC-001 confirm_appointment() sets status to "booked" instead of "confirmed" D1 Functional

Location: backend/services/appointment/lifecycle_service.py, lines 449-450

Bug: confirm_appointment() validates status is "booked"/"tentative", then sets it to safe_enum_parse("AppointmentStatus", "booked", "booked") — writing "booked" back instead of "confirmed". The entire confirmation workflow is a no-op.

Impact: Appointments never transition to CONFIRMED status. The REMINDED, CHECKED_IN, and COMPLETED lifecycle stages downstream of CONFIRMED are unreachable through the normal flow.

# BEFORE (line 449):
confirmed_status = safe_enum_parse("AppointmentStatus", "booked", "booked")

# AFTER:
confirmed_status = safe_enum_parse("AppointmentStatus", "confirmed", "confirmed")

▶ Critical PERF-001 time.sleep(0.3) blocks async event loop in advisory lock retry D6 Performance

Location: backend/routes/scheduler/_helpers.py, lines 821-826

Bottleneck: Advisory lock acquisition uses time.sleep(0.3) (stdlib blocking sleep) in 3 retry attempts. Under concurrent booking load, this serializes all request processing — blocking the event loop for up to 0.9 seconds per contending request.

What Is Working Correctly

  • Advisory lock-based booking serialization — pg_try_advisory_xact_lock with retry correctly prevents double-booking at the database level. The lock key derivation (user_id * 1M + epoch_seconds) is a sound approach for per-user slot-level locking.
  • Multi-source conflict detection — The cross-source conflict engine checks 4 calendar sources (scheduler_appointments, legacy appointments, blocked_times, Google/Outlook sync) in a unified query. This is architecturally superior to most scheduling systems which only check their own table.
  • Graduated no-show recovery — The 4-step recovery sequence (gentle SMS → understanding email → reschedule offer → final email) with configurable timing and opt-out is a well-designed workflow that respects borrower experience.
  • HMAC webhook signature set AFTER custom headers — The fix from v2 NC6 is correctly implemented at scheduler_webhook_service.py line 159 — custom headers cannot override the signature.
  • Public booking PII stripping in postMessage — EmbedBooking.js correctly strips PII from cross-origin messages, sending only appointment_id, status, and scheduled_start.
  • Dual availability system — The fallback from RecurringAvailability tables to JSON working_hours provides backward compatibility without forcing migration.
  • Slot deduplication with composite key — The NC1 fix using (start_time, user_id) composite key correctly deduplicates slots in team views.
  • SlotHold is already DB-backed — Despite previous concern, hold_manager.py correctly uses SQLAlchemy model with db.add() and db.flush(). Multi-worker safe.
  • Comprehensive audit logging infrastructure — SchedulerAuditLog model captures organization_id, user_id, action, entity_type, entity_id, changes, IP, user-agent, and booking_source. The schema is well-designed even if some callers don't populate all fields.
  • Per-org no-show recovery iteration — The v3-C6 fix correctly iterates SELECT DISTINCT organization_id before processing each org's no-shows, providing proper tenant isolation.
  • Unsigned calendar webhook token rejection — NC4 fix correctly rejects legacy unsigned tokens instead of accepting them as valid.
  • Team member IDOR validation on public booking — NC5 fix validates that team_member_id belongs to the booking link's organization before accepting.

Integration Risk Surface

  • Pipeline appointment trigger → CRM: pipeline_appointment_trigger.py creates appointments when loan stages change. If the trigger fires during a compliance scheduling evaluation, race conditions between the two creation paths could produce duplicate appointments.
  • Google/Outlook calendar sync → Conflict detection: Inbound sync creates records in external_calendar_events. If sync is delayed, the cross-source conflict engine may have stale data, allowing bookings that conflict with recently-created external events.
  • No-show recovery → Notification service: Recovery uses NotificationService directly (bypassing scheduler_sms_sender), creating an uncontrolled SMS pathway. All SMS should flow through a single consent-gated entry point.
  • Webhook dispatch → Response latency: Webhook delivery is inline with appointment operations. External endpoint latency directly impacts user-facing response times. Must be moved to background processing.
